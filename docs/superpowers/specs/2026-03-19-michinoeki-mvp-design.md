# 道の駅システム MVP 設計書

## 1. 背景と課題

全国の道の駅は 1000 駅以上あり、それぞれが独自の Web サイトや情報発信手段を持っている。そのため利用者は、営業時間、定休日、所在地、イベント情報などを確認するために、個別のサイトを都度探して確認する必要がある。

特に次のような課題がある。

- 情報が分散しており、横断的に探しにくい
- 急な定休日や営業時間変更に気づきにくい
- イベント情報や各駅の魅力に接触する機会が少ない
- 初めて訪れる利用者にとって比較や検討がしづらい

本プロダクトは、こうした分散情報をひとつにまとめ、道の駅の情報を探しやすくする基盤を作ることを目指す。

## 2. プロダクトの方向性

### 2.1 長期ビジョン

将来的には、単なる情報集約サイトではなく、次のような要素を持つ道の駅情報プラットフォームへ発展させる。

- 利用者が道の駅の情報を横断的に探せる
- 利用者同士が交流し、口コミや写真を投稿できる
- 道の駅の管理者が公式情報を発信できる
- お気に入りや通知を通じて継続的に情報を受け取れる

### 2.2 MVP の位置づけ

MVP では上記を一度に実現しない。最初の目的は、全国の道の駅を対象に、最低限の基本情報を一元化して検索できる利用者向けサイトを成立させることとする。

MVP の核価値は次のとおり。

- 全国の道の駅をひとつの入口から探せる
- 個別サイトを回らなくても、最低限の基本情報を確認できる
- 将来的な情報更新、交流、管理者投稿の土台になる

## 3. MVP のスコープ

### 3.1 対象範囲

- 対象は全国の道の駅
- ただし各駅の情報は最初から完璧である必要はない
- まずは最低限の基本情報を、可能な限り統一フォーマットで提供する

### 3.2 MVP に含めるもの

- トップページ
- フリーワード検索
- 都道府県での絞り込み
- 検索結果一覧ページ
- 道の駅詳細ページ
- 全国の道の駅マスタデータの保持

### 3.3 MVP に含めないもの

初期版では次の機能は対象外とする。

- 地図検索
- 現在地周辺検索
- 口コミ、写真投稿、交流機能
- お気に入り、通知
- 管理者アカウント
- お知らせ更新の本格集約
- 設備の複合条件による高度な検索

## 4. ユーザー体験

MVP の利用者体験は、全国版の道の駅ディレクトリとして迷わず使えることを最優先とする。

### 4.1 想定する基本導線

1. 利用者がトップページに来訪する
2. 駅名、都道府県、所在地の一部などで検索する
3. 一覧ページで候補を確認する
4. 詳細ページで各駅の基本情報を確認する

### 4.2 主要画面

#### トップページ

- サービスの価値を簡潔に伝える
- 駅名や地名で検索できる検索ボックスを配置する
- 全国の道の駅を探せる入口として設計する

#### 検索結果一覧ページ

- 検索条件に一致する道の駅を一覧表示する
- 各駅の主要情報を比較しやすくする
- 詳細ページへの導線を明確にする

#### 道の駅詳細ページ

- 各道の駅の基本情報を確認できる
- 公式サイトなど外部情報源への導線を持つ
- 将来、口コミやお知らせを追加できる情報ハブとして位置づける

## 5. データ戦略

### 5.1 基本方針

MVP では、外部サイトをリアルタイム参照するのではなく、道の駅データを自前で保持する。

この方針を採る理由は次のとおり。

- 横断検索を安定して提供できる
- 表示項目を統一できる
- 将来の機能拡張で道の駅を共通 ID で扱える
- データ取得元や最終確認日を持つことで運用改善につなげやすい

### 5.2 初期データの考え方

- 初期版は、公開データや既存情報源を活用して全国分を投入する
- データ欠損は許容し、後から補完可能なモデルにする
- 最初から全項目を埋めるより、全国を同一フォーマットで保持できることを優先する

## 6. データモデル方針

データ項目は初期から広めに定義する。ただし、すべてを同一レイヤーで扱わず、役割ごとに整理する。

### 6.1 基本情報

主に検索、一覧、詳細ページの基礎表示に使う項目。

- 名称
- 都道府県
- 所在地
- 緯度
- 経度
- 電話番号
- URL
- 道の駅登録日
- 立地道路名
- 標高
- 営業時間
- 定休日

### 6.2 詳細情報

駅ごとの魅力や補足説明として詳細ページで価値を出す項目。

- 道の駅の概要
- 道の駅の一押し
- おすすめメニュー
- お土産
- 周辺観光地
- 周辺温泉施設
- スタンプの置き場所
- スタンプの押せる時間

### 6.3 構造化設備情報

将来の絞り込み検索に使えるため、文章ではなく構造化データとして保持する。

#### 駐車台数

- 普通車
- 障がい者用
- 大型車

#### 設備フラグ

- ショップ
- お土産どころ
- 博物館・美術館
- 公園
- 展望台
- 体験施設
- ドッグラン
- キャンプ場
- 宿泊施設
- 電気自動車施設
- 無線 LAN
- 温水洗浄便座
- 道の駅切符
- 足湯
- 入浴施設
- 温泉

### 6.4 運用補助項目

- データ取得元
- 最終確認日

## 7. システム構成

MVP のシステムは、過度に複雑にせず、次の 3 層を基本とする。

### 7.1 フロントエンド

- 利用者向け画面を提供する
- 検索、一覧、詳細ページを担う

### 7.2 バックエンド

- 道の駅データを API として提供する
- 検索条件の解釈、一覧取得、詳細取得を担う

### 7.3 データ基盤

- 道の駅マスタを保持する
- 初期投入や将来の更新処理を担う

### 7.4 想定フロー

1. 公開データや既存情報源から初期データを収集する
2. データを整形して道の駅マスタへ保存する
3. フロントエンドから検索条件を受け取る
4. 一覧結果や詳細情報を返す

## 8. 検索設計

MVP の検索体験は、機能の多さよりも使いやすさを優先する。

### 8.1 MVP で提供する検索

- フリーワード検索
  - 駅名
  - 都道府県
  - 所在地の一部
- 都道府県による絞り込み
- 一覧から詳細ページへの遷移

### 8.2 あえて後回しにする検索

- 地図検索
- 現在地検索
- 設備の細かい複合フィルタ
- 並び順の細かいカスタマイズ

### 8.3 検索設計の意図

- まず誰でも使える全国版ディレクトリを成立させる
- 初期 UI をシンプルに保つ
- DB 側では将来のフィルタ拡張に耐えられる形を維持する

## 9. 将来拡張の前提

MVP は小さく作るが、次の拡張が可能な前提で設計する。

### 9.1 想定する拡張

- 臨時休業、営業時間変更、イベントなどの最新情報
- 口コミ、写真、訪問記録などのユーザー参加機能
- 道の駅管理者による公式情報投稿
- お気に入り登録や通知

### 9.2 MVP 時点で設計に織り込むこと

- 道の駅ごとの一意な ID を持つ
- 基本情報と追加情報を分離可能なモデルにする
- データ取得元と最終確認日を保持する

## 10. MVP 成功条件

MVP の成功条件は、次の状態を満たすこととする。

- 全国の道の駅を対象に最低限の基本情報を保持できている
- 利用者が駅名や地域名から対象の道の駅を検索できる
- 一覧ページと詳細ページで基本情報を把握できる
- 将来の情報追加や機能拡張に耐えられるデータ基盤の形になっている
